# M4 순차 온보딩·목업 인증·소속 학교 일치 계획

Last updated: 2026-11-08 20:36 +0900

## 1. 결론

이메일 인증의 규칙은 순수 함수 모델(`src/utils/mockAuth.ts`)로 따로 둔다. 인증 상태는 게임 Provider처럼 App 바깥에 둬서 화면을 다시 열어도 유지되게 한다. 지금 세 폰 화면에 섞여 있는 UI는 단계 컴포넌트로 나눈다. 그 위에 **한 폰에서 이메일 → 코드 → 프로필 → 캠퍼스로 넘어가는 순차 경로**를 새로 만들고, 기존 3단 비교 화면은 그대로 둔다. 인증을 마치면 이메일 도메인으로 정해진 학교 ID가 플레이어 정보에 들어간다. 그 뒤로는 고정값 `MY_SCHOOL_ID` 대신 이 값이 게임·순위·지도·채팅의 "내 학교"가 된다.

- **범위:** [Issue #15](https://github.com/Lemnoideae/261106-mkup/issues/15) 4장의 M4 작업 제안과 완료 기준 7개.
- **필수 기능과의 관계:** 기획서 4-1 #4 "대학 이메일 인증"(필수)과 시나리오 1의 ①~③(이메일 입력 → 코드 제출 → 서버가 정한 소속 학교로 참여)을 목업에서 재현한다. 실제 메일 발송·서버 검증은 하지 않는다.
- **선행 묶음:** M1(학교 ID·공통 조회)과 M2(지도·방문)는 병합됐다(PR #26, #27). M1의 로고 판정은 사용자 지시(2026-11-08 "로고는 임시 배지로 인정")로 해소됐다(`docs/261108-1930-m1_school_map_data_plan.md` 8-1절).
- **결정:** 6장의 D1~D5는 사용자 지시("좋아, 기본안대로 진행해줘.", 2026-11-08)로 기본안을 적용했다.
- **상태:** M4-A~D 구현과 자동 테스트 완료. 결과는 9장.

## 4. 작업 계획

### 4-1. M4-A 목업 인증 모델 (순수 함수, 화면 없음)

`src/utils/mockAuth.ts`에 상태와 동작을 둔다. 시간(`now`)과 코드 생성기는 인자로 받아 테스트에서 고정한다.

| 동작 | 규칙 |
|---|---|
| `requestCode(email)` | 앞뒤 공백을 지우고 소문자로 바꾼다. 형식이 틀리면 `invalid-email`, 목록에 없는 도메인이면 `unsupported-domain`, 학교가 둘 이상인 도메인이면 `ambiguous-domain`으로 거절한다. 통과하면 학교 ID가 정해지고 코드가 발급된다(유효시간, 시도 횟수 0, 재발송 가능 시각 기록) |
| `verify(code)` | 순서대로 검사한다. ① 이미 사용한 코드면 `already-used`(아무것도 바뀌지 않음) ② 만료면 `expired` ③ 시도 한도를 다 썼으면 `locked` ④ 틀리면 시도 +1, `wrong-code`(남은 횟수 표시) ⑤ 맞으면 인증 정보(이메일·학교 ID·인증 시각)를 기록하고 코드를 사용 처리 |
| `resend()` | 대기 중이면 `cooldown`(남은 초 표시). 대기가 끝났으면 새 코드를 발급하고 이전 코드를 무효로 만든다. 시도 횟수는 새 코드 기준으로 다시 센다 |
| `editEmail()` | 코드와 인증 정보를 모두 지우고 이메일 단계로 돌아간다 |
| `completeProfile(nickname, departmentId)` | 인증 정보가 없으면 `not-verified`. 닉네임은 공백을 뺀 1~10자여야 하고, 학과는 그 학교의 목록에 있어야 한다. 이미 완료했으면 `already-completed`(다시 실행하지 않음) |

- **학교는 사용자가 고르지 않는다.** 도메인으로 정해진다. 시나리오 1 ③의 "서버가 확정한 소속 학교"에 해당한다.
- 샘플 도메인 표(`src/data/mockEmailDomains.ts`, D1)는 학교 ID에 연결하고, 공통 목록에 없는 ID를 가리키지 않는지 테스트로 검사한다.
- 시도 한도와 재발송 대기는 따로 관리한다. 한도를 넘어 잠긴 상태에서 벗어나는 방법은 대기 뒤 재발송뿐이다. 다시 입력하거나 화면을 다시 열어도 풀리지 않는다.

### 4-2. M4-B 인증 상태의 위치와 순차 화면

- **상태 위치:** `MockAuthProvider`(`src/hooks/useMockAuth.tsx`)를 `src/main.tsx`에서 `MockGameProvider`와 같은 높이에 둔다. 온보딩 화면을 닫았다 다시 열어도(컴포넌트가 다시 마운트돼도) 시도 횟수와 코드가 남는다. 남은 시간은 250ms 간격으로 다시 계산한다. 게임 버프 타이머(`src/hooks/useMockGame.tsx:71`)와 같은 방식이다.
- **단계 컴포넌트로 분리:** `OnboardingFlow.tsx`의 폰 세 대를 `EmailStep`, `CodeStep`, `ProfileStep`(`src/components/onboarding/`)으로 나눈다. 각 단계는 표시할 값과 콜백을 props로 받는다.
- **순차 단일 폰:** `OnboardingPhone`이 인증 상태의 단계에 맞는 컴포넌트 하나만 보여 준다. 시연 메뉴에 "📱 순차 온보딩 (Single Phone)" 진입점을 추가한다(D3).
- **3단 비교 화면 유지:** 기존 "3단 온보딩 화면"은 같은 단계 컴포넌트에 고정 샘플 값을 넣어 세 폰을 나란히 보여 준다. 이 화면은 인증 상태를 바꾸지 않는다.
- **목업 메일함:** 실제 메일을 보내지 않으므로, 코드 단계에 "목업 메일함 (실제 발송 없음)" 상자를 두고 발급된 코드를 보여 준다. "인증 메일이 날아갔어!" 같은 문구는 "목업 코드가 발급됐어"로 바꾼다. 시연용 "만료 시연" 버튼은 D4에 따른다.
- **오류 표시:** 위 거절 사유마다 `role="alert"` 문구를 둔다. 남은 시도 횟수와 재발송 대기 초를 보여 준다.

### 4-3. M4-C 완료 정보와 소속 학교 일치

- **완료 데이터:** `{ email, schoolId, departmentId, department, nickname }`를 `setPlayer`로 넘긴다. 이름이 아닌 ID가 기준이다.
- **내 학교 ID를 동적으로:** `getSchoolRankings(schoolScore, mySchoolId)`, `getSchoolViews(schoolScore, mySchoolId)`, `getMockRankings(state, player)`가 `player.schoolId`를 쓰게 한다. `MY_SCHOOL_ID`는 기본 플레이어의 학교로만 남긴다. App의 내 학교 판정(`:82`)도 `player.schoolId`와 비교한다.
- **표시 일치:** 3-2 표의 고정 위치를 플레이어의 학교 정보(공통 목록의 이름·첫 글자·배지색)로 바꾼다. 대상은 HUD, 헤더 기본 이름, 채팅 작성자, 우리 학교 방명록 이름, 순위 탭 문구, 이미지 상점 대상, 응원 문구다.
- **학과 목록:** `KNOWN_DEPARTMENTS`를 학교별 목록으로 정리한다. D1의 샘플 학교마다 3~5개씩 두고, 한양대에서 두 이름이 `my-department`를 같이 쓰는 문제도 풀어 학과 ID와 이름이 하나씩 대응하게 한다.
- **지원금 안내:** "8,420점"을 `INITIAL_CONTRIBUTION`에서 계산한 값으로 바꾼다.
- **한빛대 제거:** 도메인 칩, 문장 이미지, 축하 문구, 학생증의 고정 학교를 인증된 학교 값으로 바꾼다. 비교 화면은 샘플 학교 값을 쓴다.

### 4-4. M4-D 재시연과 게임 상태 (D2)

- `gameReducer`에 `reset` 동작을 추가한다. 이 동작은 기여도, 학과 점수, 클리커, 버프를 초기값으로 되돌리고, 학교 점수는 새 학교의 공통 목록 초기 점수로 설정한다. Provider는 `resetForSchool(schoolId)`로 노출한다.
- 완료할 때 다음 규칙을 적용한다.
  - 기존 플레이어와 **다른 학교**면 반드시 초기화한다. 완료 화면에 "새 학교로 처음부터 시작" 안내를 보인다.
  - **같은 학교**면 "진행 유지 / 처음부터" 중 하나를 고르게 한다. 다른 학교 점수로 조용히 합치는 경로는 없다.
