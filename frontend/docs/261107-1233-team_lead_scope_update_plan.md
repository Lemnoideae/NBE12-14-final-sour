# 팀장 추가 요청 반영 계획 및 기존 계획 충돌 검토

Last updated: 2026-11-09 18:44 +0900

## 1. 결론과 문서 상태

**기존 M1·M2를 폐기하지 않고, 공통 식별·이미지 데이터를 확장한 뒤 상점 개편과 연합·대결 4개 화면을 추가하는 방안을 권고한다.** 직접 변경해야 할 기존 방침은 ‘커피 외 아이템도 검토 중 시안으로 노출’하는 부분이다. 이미지 변경 상품의 현금 결제는 기존 기여도 구매와 분리해야 한다.

- **요청 출처:** 2026-11-07 현재 대화에서 사용자가 인용한 팀장 메시지와 이후 사용자 추가 지시 1–4번. 후속 지시로 수치는 임시 변수화, 소속 구성원의 공용 이미지 변경 권한·전체 화면 즉시 공유, 이미지 즉시 적용, 연합 간 대결 관계를 구체화했다.
- **문서 상태:** 사용자 확정 정책과 구현 권고를 구분한 실행 계획이다. 확정 정책은 아래 2-1절을 따르며, 문서 수정이 구현·검증 완료를 뜻하지 않는다.
- **확인:** 기획서 4장·6장·10장·11장, 기존 계획 4개와 현재 소스를 읽었다. 소스 기준 HEAD는 `d5bbd42`이다. 파일·행 인용은 이번 조사 시점 기준이다.
- **구현 범위와 요구의 구분:** 현재 작업 묶음은 프런트엔드 목업이며 실제 결제·이미지 업로드 서버·이메일 인증·다중 사용자 연합·경기 집계·보상 정산은 별도 서비스 작업이다. 다만 **이미지 변경을 모든 사용자의 현재 화면에 즉시 반영하는 것은 확정 요구**다. 목업에서는 공유 상태·다중 사용자 시뮬레이션으로 검증하고, 실제 서로 다른 브라우저/기기 간 즉시 전파는 서버 이벤트 연동과 별도의 완료 기준을 둔다. 후자를 로컬 화면 갱신만으로 완료 처리하지 않는다.
- **표기:** ‘팀장 요청’은 전달된 요구, ‘기획서’는 원문, ‘확인’은 파일/명령으로 확인한 사실, ‘추론’은 해석, ‘권고’는 아직 승인되지 않은 제안, ‘미확정’은 추가 결정이 필요한 사항이다.
- 기존 승인 문서와 결과 보고서는 이력으로 보존한다. 이번에는 이 문서만 수정하며, 다른 문서를 덮어쓰거나 구현·완료 체크를 변경하지 않는다. 이후 실행 시에는 이 문서의 확정 정책·변경 대조표와 기존 계획을 함께 읽는다.

기획서 4-2의 연합·커스텀 로고는 기본 MVP 필수가 아닌 선택 기능이다. **현재 팀장 요청을 근거로 이번 추가 목업 범위에 포함**하며, 선택 목록에 있다는 이유로 배제하지 않는다. 반대로 이번 요청만으로 연합 채팅·실결제·보상 정산까지 모두 필수가 되는 것은 아니다.

### 2-1. 후속 사용자 지시로 확정된 정책

| 출처 | 확정 정책 | 적용 경계 |
| --- | --- | --- |
| 사용자 지시 1번 | 정확한 수치는 추후 검토하며 현재는 임의 값의 변수로 구성 | 가격·기간·효과량은 공통 설정값을 사용하고 UI·계산·테스트에서 숫자를 따로 하드코딩하지 않는다. |
| 사용자 지시 2번 | 소속 학교 구성원 누구나 학교 이미지 변경 가능, 소속 학과 구성원 누구나 학과 이미지 변경 가능 | 대표자 전용 권한을 추가하지 않는다. 다른 학교·다른 학과 이미지는 변경할 수 없다. 개인 프로필은 본인만 변경한다. |
| 사용자 지시 2·3번 | 공용 이미지는 모두가 공유하고 변경 즉시 모든 사용자 화면에 적용 | 변경자뿐 아니라 같은 학교/학과 구성원 및 해당 이미지를 보고 있는 외부 사용자 화면도 갱신한다. 개인 프로필도 본인이 바꾸면 이를 표시하는 다른 사용자 화면에 갱신한다. |
| 사용자 지시 3번 | 이미지 변경은 즉시 적용 방식 | 결제·변경 성공 시 바로 적용하며 변경권 인벤토리·나중에 사용하기 단계를 만들지 않는다. 실패·취소 시 기존 이미지를 보존한다. |
| 사용자 지시 4번 | 대결의 숫자는 학교 수 기준, 한 연합의 상대는 한 연합 | 2:2는 학교 2개로 구성된 연합끼리, 3:3은 학교 3개로 구성된 연합끼리 대결한다. **해석:** 한 연합은 동시에 하나의 상대 연합과만 대결하며, 종료 후에는 다른 상대와 대결할 수 있다. 평생 고정 상대라는 뜻으로 확대하지 않는다. |

### 2-2. 수치 설정 원칙과 임시 값

아래 변수명·값은 **목업 구현 권고/임시 값**이다. 기존 `src/data/gameRules.ts`의 공통 설정을 확장하거나 용도별 설정 모듈로 분리하고, 컴포넌트·reducer·시계·테스트가 같은 설정을 읽게 한다. 실제 변수 선언은 구현 작업에서 수행한다.

| 설정 예시 | 목업 초기값 | 의미 |
| --- | --- | --- |
| `COFFEE_PRICE` / `COFFEE_CURRENCY` | `120` / `contribution` | 기존 커피 구매를 재사용하는 임시 가격·통화. 이미지 상품의 현금 통화와 구분한다. |
| `IMAGE_CHANGE_PRICES_KRW` | `{ school: 500, department: 500, profile: 500 }` | 최초 팀장 메시지의 500원을 기본값으로만 재사용하며 유형별 조정 가능 |
| `COFFEE_DURATION_MS` / `COFFEE_MULTIPLIER` | `30_000` / `2` | 커피 효과·지속시간의 임시 값 |
| `BATTLE_DURATION_HOURS` | `{ min: 6, max: 72, default: 24 }` | 최소 6시간은 원문에서 가져오고 최대·기본은 시연용으로 채운 값. 모두 추후 조정 가능하며 원문의 ‘최대 n일’을 72시간으로 확정한 것이 아님 |
| `BATTLE_FORMAT_SCHOOL_COUNTS` | `[2, 3]` | 기획서의 2:2·3:3을 학교 수로 표현하는 초기 시연 형식. 각 값은 양쪽 연합에 같은 수로 적용 |

- 점수 샘플·기존 강화 비용·성장 기준도 기존 공통 데이터에서 읽는다. 형식에 필요한 수의 학교 샘플을 제공하고, 가격·기간을 바꿔도 화면 문구·검증 경계가 함께 바뀌게 한다.
- **정책 불변식은 밸런스 변수와 구분:** ‘한 연합의 동시 상대는 최대 하나’, ‘동일 소속 구성원에게 변경 권한’, ‘전체 화면 즉시 반영’은 임의 숫자 조정으로 끄거나 완화할 수 있는 옵션이 아니다. 기획서 11장의 서비스 성능 목표도 이번 가격·기간 임시화로 변경하지 않는다.

## 5. 추가 작업 계획

새 작업은 N1–N4로 구분하고 기존 M1–M7 번호를 유지한다. 2-1절의 사용자 확정 정책은 그대로 적용하고, 아래 데이터명·전파 방식·화면 구조·상태 전이는 **구현 권고**로 구분한다. 최종 DB/API 설계는 아니다.

### N1. 학교·학과·개인 이미지 데이터와 공통 표시

- 학교는 기존 `schoolId`, 학과는 학교에 연결된 `departmentId`, 본인은 안정적인 `userId`로 조회한다. 첫 목업은 명시적인 샘플 ID를 써도 되지만 이름 변경으로 이미지가 사라지거나 다른 대상에 적용되면 안 된다.
- 학교의 기본 로고와 유료 커스텀 이미지는 별도로 보존하고, 학과·개인에도 현재 이미지 URL을 둔다. 예시 필드명은 `defaultLogoUrl`·`customImageUrl`·`profileImageUrl`이며 실제 위치는 구현 시 정한다.
- **목업 권고:** 관리된 로컬 샘플 이미지와 URL 입력·미리보기를 제공한다. 빈 값·허용하지 않는 스킴·이미지 로드 실패를 구분하고 기존 이미지/배지로 복구한다. 외부 URL 입력 허용만으로 안전한 업로드 서비스가 완성된 것은 아니다.
- 표시 대상은 학교: 지도·순위·방문·연합·대결, 학과: 학과 순위 및 변경 미리보기, 개인: 내 프로필 요약·개인 순위 및 작성자 표시를 우선한다. 해당 이미지가 없는 기존 화면에 새 프로필 영역을 무조건 늘리지는 않는다.
- **사용자 확정:** 학교 이미지는 해당 학교 소속 누구나, 학과 이미지는 해당 학교·학과 소속 누구나 변경한다. 학교 소속이 같아도 다른 학과 이미지는 변경할 수 없다. 개인 프로필은 본인만 변경한다. 실제 서비스에서는 로그인한 사용자의 검증된 소속으로 서버가 권한을 검사하며 클라이언트가 보낸 소속 값만 신뢰하지 않는다.
- **사용자 확정:** 공용 이미지는 개인별 복사본이 아닌 대상 ID별 공유 값이다. 변경 성공 직후 지도·순위·방문·연합·대결 및 작성자 표시 등 **해당 이미지가 보이는 모든 사용자의 현재 화면**에 반영하며 새로고침·화면 재진입을 요구하지 않는다. 다른 학교 사용자의 화면도 해당 대상을 표시 중이면 갱신한다.
- **목업 권고:** 이미지 저장소를 화면 밖 공통 상태로 두고 대상 ID별 변경 구독으로 모든 표시를 갱신한다. 두 사용자 컨텍스트를 동시에 렌더링하는 통합 테스트로 공유 반영을 시연한다. 이를 별도 브라우저/기기 간 전파 완료로 표현하지 않는다.
- **서비스 전파 권고:** 서버가 권한·변경 성공을 확정한 뒤 대상 종류·ID·최신 URL·리비전의 변경 이벤트를 발행하고 클라이언트 공통 캐시를 갱신한다. 오래된 이벤트는 무시하고 이미지 URL/리비전을 갱신해 브라우저·CDN 캐시가 이전 이미지를 계속 보이지 않게 한다. 재연결·새 접속 때 최신 값을 다시 동기화한다. ‘즉시’는 성공 확정 후 전파를 시작하고 이벤트 수신 시 다음 렌더에 반영한다는 의미이며 네트워크·이미지 다운로드 지연이 0이라는 보장은 아니다.
- **대안·권고:** 주기 조회는 구현이 단순하지만 갱신 간격만큼 지연된다. 현재 즉시 반영 요구에는 서버 변경 이벤트 구독을 권고하며 구체 전송 기술은 연동 시 정한다. 가격처럼 갱신 지연을 임의의 긴 대기 값으로 두어 요구를 축소하지 않는다.
- 캠퍼스 성장 이미지는 별개다. 로고 변경 때문에 캠퍼스 단계 이미지나 성장 점수 기준을 바꾸지 않는다.

| 연합 신청 | 내 학교, 대상 학교 검색·선택, 선택 학교 로고/이름, 신청 요약, 신청 버튼, 보낸/받은 요청 | 검색 0건, 신청 대기, 취소, 수락·거절 결과, 중복/자기 학교 선택 거절, 요청 실패·재시도 |
| 현재 연합 조회 | 연합명·상태, 참여 학교 목록·로고, 대기 요청, 대결 신청/현황 진입, 뒤로가기 | 소속 연합 없음, 신청 중, 연합 성립, 조회 실패·재시도. 학교 선택 시 방문 연결은 M2와 통합 |

- ‘현재 연합’은 **내 학교가 속한 연합 조회**로 우선 해석한다. 모든 연합의 공개 탐색 목록까지 요구한 것인지는 확인한다.
- 목업 상태는 `신청 대기 → 수락/거절/취소`, 수락 후 참여 학교가 일치하는 연합이 생기는 최소 흐름을 권고한다. **상대 학교 수락은 시연용 상태 제어로 구분**하고 내가 일반 사용자 화면에서 상대 학교를 대신 승인하지 않게 한다.
- 신청자·수신 학교·참여 학교를 ID로 관리하고 같은 실행 중 다른 화면을 다녀와도 유지한다. 대표자 권한·한 학교의 복수 연합 가입·정원·탈퇴/해산은 미확정이다.
- 목업 데이터는 2:2·3:3의 양쪽 연합과 동시 상대 제한을 재현할 제3 연합을 제공한다. 각 연합 구성원은 사람이 아닌 학교 ID 목록이다. 이는 ‘학교당 1개 연합’이라는 실제 정책 확정이 아니다. 탈퇴·해산 관리 UI와 연합 채팅은 이번 4개 화면의 선행 조건으로 삼지 않는다.

#### N3 완료 기준

- [ ] 연합 신청 화면과 현재 연합 화면에 각각 진입·복귀할 수 있다.
- [ ] 신청 → 대기 → 시연 수락 후 신청·조회 화면의 연합/학교 ID와 상태가 일치한다.
- [ ] 자기 학교·중복 요청·유효하지 않은 ID를 거절하고 빈 상태·실패·재시도를 정해진 조작으로 재현한다.
- [ ] 연합 조회 화면의 참여 학교가 N1의 최신 이미지·학교명을 읽고, 화면 이동으로 게임 상태가 초기화되지 않는다.

### N4. 대결 신청 화면과 대결 현황 화면

| 화면 | 기본 구성 | 시연할 상태·행동 |
| --- | --- | --- |
| 대결 신청 | 내 연합·상대 연합, 양측 참여 학교/로고·학교 수, 대결 형식, 설정 기반 시작·종료/기간, 조건 요약, 신청 버튼 | 연합 없음, 상대 없음, 자기 연합/참여 학교 중복, 학교 수 불일치, 상대 또는 내 연합 대결 중, 잘못된 기간, 신청 대기, 취소, 시연 수락·거절, 실패·재시도 |
| 대결 현황 | 신청/예정/진행/종료 구분, 양측 학교·연합, 점수·점수 차, 시작/종료·남은 시간, 결과 안내 | 경기 없음, 신청 대기, 진행 중, 종료·무승부 샘플, 조회 실패·재시도, 신청 화면 복귀 |

- **기획서 배경:** 4-2는 2:2·3:3, 최소 6시간~최대 n일, 승리 시 패배 팀 점수 배분을 제안한다. **후속 사용자 확정:** 숫자는 연합별 학교 수를 뜻하며, 각 경기는 연합 하나 대 연합 하나의 대결이다. 경기 운영·점수 이전까지 승인된 것으로 확대하지 않는다.
- **대결 형식:** 2:2는 A연합의 학교 2개 대 B연합의 학교 2개, 3:3은 학교 3개 대 학교 3개다. 신청·수락 시 양쪽의 실제 학교 ID 수가 선택 형식과 맞는지 검사한다. 사용자 수나 연합 두 개 대 연합 두 개라는 뜻으로 표시하지 않는다.
- **동시 상대 제한:** 예정·진행 중인 경기가 있는 연합은 다른 연합과의 대결을 새로 확정할 수 없다. A–B가 확정되면 A–C뿐 아니라 B–D도 거절한다. 신청 시점뿐 아니라 수락 직전 양쪽 연합의 최신 상태를 재검사한다. 대기 요청 자체의 예약 여부는 별도 구현 권고로 구분한다.
- **목업 권고:** 2:2·3:3 모두 `신청 대기 → 수락 → 예정 → 진행 → 종료` 샘플을 제공한다. 기간은 `BATTLE_DURATION_HOURS`에서 읽고 빠른 시연은 별도 시계 제어로 처리한다. 값만 바꿔 최소·최대·기본 기간 및 경계 테스트를 함께 변경할 수 있게 한다.
- **전이 권고:** 첫 수락으로 두 연합의 경기 점유를 함께 기록하고, 관련된 다른 대기 신청은 더 이상 수락되지 않게 한다. 종료·취소로 점유를 해제하면 다음 상대와 대결할 수 있다. 여러 대기 신청을 허용할지 즉시 예약할지와 경기 취소 권한은 추가 구현 정책으로 남긴다. 실제 서버에서는 양쪽 점유 검사·확정을 원자적으로 수행해야 한다.
- **목업 권고:** 대결 점수는 명시적인 경기 샘플 값으로 표시하고 기존 학교 누적 점수를 덮어쓰지 않는다. 실제 집계가 필요하면 ‘기간 중 인정 획득량’과 누적 점수 중 무엇을 쓸지 먼저 확정한다. 개인 소비로 경기 점수가 내려가게 만들지 않는다.
- 종료 결과는 샘플로 보여 주되 보상은 ‘정책 미확정·정산 미연동’으로 표시한다. 패배 학교 점수를 실제 차감하거나 다른 학교/개인에게 지급하지 않는다. 구현 승인을 받으면 원문의 점수 이전 요구와 기존 학교 점수 미차감 정책의 적용 경계를 별도로 합의한다.
- 연합 승인·대결 승인 권한과 경기 종료 후 연합 구성 변경 가능 여부는 확인 사항이다. 참여 학교 ID 구성의 스냅샷을 보관하는 방안을 권고하되, **로고·프로필 이미지는 스냅샷에 고정하지 않고 N1의 최신 공유 값을 표시**한다. 경기 화면도 이미지 변경 즉시 갱신 요구에서 제외하지 않는다.

#### N4 완료 기준

- [ ] 대결 신청·현황 화면에 각각 진입·복귀하며 같은 경기 ID와 참여 학교를 표시한다.
- [ ] 2:2·3:3 양쪽의 학교 수와 ID를 검사하고 신청·수락·예정·진행·종료·무승부 샘플 및 실패·재시도를 중복 생성 없이 재현한다.
- [ ] A–B의 예정/진행 중 A–C·B–D 확정을 거절한다. 오래 열린 수락 화면과 양쪽 연합의 연속 수락에서도 같은 제한을 검사하고, 경기 종료/취소 후에는 새 상대와 대결할 수 있다.
- [ ] 공통 설정과 고정 시계로 기간 경계·남은 시간을 검증하고 종료 후 진행 중으로 표시하지 않는다. 이미지 변경은 경기 진행·종료 여부와 관계없이 현재 화면에 반영된다.
- [ ] 경기 샘플 조회·시연 상태 변경은 실제 학교/학과/개인 점수·버프·방문 관전 규칙에 영향을 주지 않는다.

## 6. 진입 동선과 수정 우선순위 권고

**진입 동선 권고:** 기존 서비스 화면의 학교 메뉴에 ‘연합·대결’을 추가하고 `현재 연합 ↔ 연합 신청`, `현재 연합 → 대결 신청 → 대결 현황`을 연결한다. 시연용 런처에서도 요청한 4개 화면에 직접 진입할 수 있게 한다. 하단 내비게이션을 반드시 2개 더 늘릴 필요는 없다. 샘플 수락·시계 변경은 일반 사용자 조작과 구분한다.

| 순서 | 작업 묶음 | 의존성·범위 |
| --- | --- | --- |
| 0 | 확정 정책·임시 설정 정리 | 2-1절 권한·즉시 공유·학교 수·동시 상대 제한을 적용하고 2-2절 수치를 공통 설정에 둔다. 정확한 가격·기간 확정이나 이미 답한 정책 질문을 착수 선행 조건으로 삼지 않는다. |
| 1 | 기존 M1-A + N1 공통 식별·이미지 기반 | 학교·학과·사용자 식별, 소속 권한, 공통 이미지 저장소와 모든 화면 구독·다중 사용자 시뮬레이션을 구성한다. 전체 권역 지도 완성을 선행 조건으로 두지는 않는다. |
| 2 | N2 상점 축소·신규 3종·모의 결제 | N1 의존. 네 상품 노출·통화·점수 불변·실패 처리를 회귀 테스트로 고정한다. |

| 4 | N4 대결 신청·현황 | N3의 연합 샘플 재사용. 실제 경기 엔진·보상은 만들지 않는다. |

| 6 | M4·M5·M6 연계 | 인증된 소속·권한 표현, 실패·재시도, 실제 브라우저/모바일 확인을 통합한다. 기존 필수 인증·어뷰징 과제를 취소하지 않는다. M6는 각 묶음에서도 반복한다. |
| 서비스 필수 후속 | 이미지 즉시 전파 연동 | 서버 권한 확인·공유 이미지 확정·변경 이벤트·캐시 무효화·재연결 동기화 및 별도 사용자 세션 검증. 목업 단계와 나눠 기록하되 사용자 확정 요구를 선택 기능으로 내리지 않는다. |
| 별도 | M3·M7 및 기타 서비스 연동 | 채팅·방명록 개선, 로컬 새로고침 저장, 실결제·실제 연합/경기 서버는 별도 범위로 유지한다. |

**가장 강한 대안:** 기존 순서대로 M1·M2 전체를 먼저 마친 후 N1–N4를 진행하면 지도·방문 회귀 위험과 작업 전환을 줄일 수 있다. 대신 팀장이 요청한 상점·4개 화면 확인이 늦어진다. **권고:** 공통 데이터만 먼저 확보한 뒤 신규 화면을 앞당기는 위 순서다. 이는 우선순위 제안이며 기존 계획의 승인·완료 상태를 소급 변경하지 않는다.

## 7. 확정 처리한 사항과 남은 결정

**기존 질문에서 확정으로 이동:** 가격·효과·기간은 임시 설정값으로 진행, 학교·학과 소속 누구나 공용 이미지 변경, 모든 열람자 화면에 즉시 공유, 보관형 변경권 없이 즉시 적용, 학교 수 기준의 연합 간 대결과 동시 상대 하나 제한. 이 사항들을 다시 승인 대기 항목으로 남기지 않는다. 임시 값과 확정 정책의 구분은 2-1·2-2절을 따른다.

| 남은 항목 | 목업 처리·권고 | 추후 결정 시점 |
| --- | --- | --- |
| 이미지 입력·파일 저장·콘텐츠 관리 방식 | URL/로컬 샘플 미리보기로 진행한다. 파일 업로드·권리/신고·검수·환불은 별도 설계한다. | 실제 이미지 저장/결제 연동 전 |
| 누가 연합·대결을 신청·수락하나? 학교 복수 가입·연합 구성 변경은? | 이미지 변경 권한을 연합 승인 권한으로 확대하지 않는다. 목업에서는 일반 신청과 상대 수락 시연 제어를 분리하고 학교 수가 맞는 샘플로 진행한다. | 실제 연합 권한·가입 정책 구현 전 |
| 대기 중 여러 대결 신청 허용·예약 시점·취소 권한 | 예정·진행 경기의 상대 하나 제한은 확정이다. 목업은 수락 시 양쪽 점유를 검사·확정하고 그 외 대기 신청을 수락 불가로 전환하는 방안을 권고한다. | 신청 큐·취소 전이 확정 시 |
| 실제 경기 득점·무승부 처리·보상 정산 | 점수·결과는 샘플, 기간·효과량은 공통 임시 설정으로 진행한다. 실제 클릭 집계와 점수 이전 방식은 별도 정책으로 남긴다. | 실제 득점·보상 구현 착수 전 |

남은 사항은 목업 초안 전체의 선행 조건이 아니다. 최종 밸런스·서비스 정책·실시간 서버 검증을 완료한 것처럼 기록하지 않는다.

## 8. 검증 계획·회귀 센서

- **상품/통화·설정 센서:** 허용 상품 ID 집합이 커피+신규 3종인지, 각 가격·통화·효과·기간이 공통 설정과 일치하는지, 제외 ID 직접 구매가 거절되는지 검사한다. 기본값뿐 아니라 다른 임시 설정을 주입해 UI·금액 판정·기간 경계가 함께 바뀌는지 테스트한다.
- **점수/버프 불변:** 이미지 변경 성공·취소·실패에서 개인/학교/학과 점수·클리커·버프 종류/만료시각이 유지되는지 시간을 고정해 비교한다. 별도 시간 진행에서는 커피가 정상 만료돼야 한다.
- **이미지 식별·권한:** 동명 학과·닉네임 변경·잘못된 ID·이미지 오류와 학교 소속/학과 소속/본인 여부를 조합해 허용·거절을 검사한다. 같은 학교 다른 학과 사용자는 학교 이미지는 바꿀 수 있지만 해당 학과 이미지는 바꿀 수 없어야 한다.
- **공유 즉시 반영:** 두 사용자 컨텍스트에서 같은 대상의 여러 화면을 동시에 열고 변경 즉시 갱신되는지, 취소·실패 시 모두 기존 값인지 검사한다. 별도 세션 통합 시험에서는 서버 이벤트·역순 리비전·브라우저/CDN 캐시·재연결과 외부 학교 열람자도 검사한다. 목업 성공을 실제 사용자 간 전파 완료로 간주하지 않는다.
- **상태 전이·학교 수·상대 제한:** 신청 중 중복 조작, 수락/거절/취소 재처리, 자기 자신·학교 ID 중복, 선택한 학교 수와 실제 구성 불일치, 설정 기반 기간 경계를 검사한다. A–B 확정 뒤 A–C·B–D 거절, 연속 수락·오래된 수락 화면, 종료/취소 후 점유 해제를 회귀 테스트로 고정한다. 로컬 검사 통과를 서버의 원자성·동시성 검증으로 표현하지 않는다.
- **4개 화면 접근:** 각 화면 직접 진입, 신청→조회/현황 연결, 뒤로가기, 빈 목록·실패·재시도, 게임 Provider 수명과 기존 M2 관전 규칙을 DOM 통합 테스트로 남긴다.
- **기존 테스트 변경:** 기존 깃발/열람권 구매 시나리오는 제외 상품 거절·커피 재구매·이미지 구매의 버프 불변 검사로 갱신한다. 향후를 위해 1회 버프 엔진을 남긴다면 비판매 테스트 fixture로 엔진 불변식을 유지하되 일반 판매 목록에 재노출하지 않는다. 테스트 개수만 유지하는 것을 목표로 하지 않는다.
- **실행 검사:** 구현 시 `npm run test`, `npm run lint`(현재 `tsc --noEmit`), `npm run build`, `git diff --check`, 변경 소스의 사용 가능한 활성 LSP 진단을 실행한다. 이는 `package.json:6`–`:12`의 현재 스크립트 기준이다.
- **실제 화면:** 모바일·데스크톱에서 이미지 크롭/오류 대체, 긴 학교·학과명, 가격/통화, 미리보기·결제창 스크롤, 4개 화면 복귀·포커스·터치를 M6로 확인한다. 차단 시 DOM 통과로 대체하지 않고 미검증 사유를 기록한다.
- **서비스화 검증 별도:** 인증된 소속·권한, 전체 사용자 이미지 변경 이벤트·순서·캐시·재연결, 결제 검증·중복 통지·동시 변경·환불/재처리, 업로드 보안·콘텐츠 정책, 연합 동시 가입·경기 양쪽 점유·중복 수락, 서버 시계·경기 집계·정산은 서버 과제다. 이미지 즉시 전파는 확정 요구의 서비스 단계 완료 기준으로 관리한다. 기획서 10·11장의 클릭 검증 및 3,000요청/초·50ms·95% 목표 충족을 목업 성공으로 주장하지 않는다.
