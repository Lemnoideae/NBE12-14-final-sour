PRICE구매 당시 가격 (스냅샷)BIGINTNN, CHECK >= 0

상태 정의 (토스 Payment status와 이름을 맞춤)

STATUS의미바뀌는 시점
READY주문 생성, 결제창 호출 전서버가 주문을 만들 때
IN_PROGRESS승인 API 호출 중서버가 승인 API를 호출하기 직전 (중복 승인 방지용 잠금)
DONE승인 완료승인 API 응답 status = DONE
ABORTED결제 실패failUrl로 돌아왔거나 승인 API가 실패했을 때
EXPIRED유효 시간 초과일정 시간 동안 READY로 남은 주문을 배치로 정리할 때
CANCELED결제 취소(환불)취소 API 응답 status = CANCELED
  • 상태 전이: READY → IN_PROGRESS → DONE → CANCELED, READY → ABORTED, IN_PROGRESS → ABORTED, READY → EXPIRED
  • 아이템은 전액 결제·전액 취소만 쓰므로 PARTIAL_CANCELED는 사용하지 않는다.
  • 가상계좌는 결제수단에서 제외한다. (WAITING_FOR_DEPOSIT 상태와 입금 웹훅 처리가 필요 없어짐)

결제 흐름

단계주체처리
1. 주문 생성서버POST /api/payments (itemId) → ITEM.PAY_TYPE이 CASH인지 확인 → PAYMENT를 READY로 INSERT (ORDER_ID = UUID, AMOUNT = ITEM.PRICE) → orderId, orderName, amount 응답
2. 결제창 호출프론트토스 SDK requestPayment에 orderId, orderName, 금액, successUrl, failUrl 전달
3-1. 인증 성공프론트 → 서버successUrl로 paymentKey, orderId, amount를 받아 POST /api/payments/confirm으로 전달
3-2. 인증 실패프론트 → 서버failUrl로 code, message, orderId를 받아 서버에 전달 → ABORTED (승인 API 호출 안 함)
4. 검증서버ORDER_ID로 조회 → 본인 주문인지, STATUS = READY인지, amount = AMOUNT인지 확인
5. 잠금서버UPDATE payment SET status = 'IN_PROGRESS', payment_key = ? WHERE order_id = ? AND status = 'READY' → 영향받은 행이 0이면 중복 요청이므로 중단
6. 승인서버 → 토스POST /v1/payments/confirm (paymentKey, orderId, amount), 헤더 Authorization: Basic base64(시크릿키 + ":")
7-1. 승인 성공서버한 트랜잭션에서 STATUS DONE, METHOD·REQUESTED_AT·APPROVED_AT 저장 + USER_ITEM INSERT → 커밋 후 Redis에 아이템 효과 적용
7-2. 승인 실패서버STATUS ABORTED, FAIL_CODE·FAIL_MESSAGE 저장

관계 및 제약

  • USER 1 : PAYMENT 0..N / ITEM 1 : PAYMENT 0..N / PAYMENT 0..1 : USER_ITEM 0..1
  • AMOUNT는 서버가 ITEM.PRICE로 확정한다. 클라이언트가 보낸 금액은 검증용으로만 쓴다.
  • 토스 승인 API 호출은 DB 트랜잭션 밖에서 한다. 외부 HTTP 호출 동안 DB 커넥션과 락을 잡고 있지 않기 위해서다.
  • 승인 API가 타임아웃 나면 실패로 단정하지 않는다. 결제 조회 API(GET /v1/payments/orders/{orderId})로 실제 상태를 확인한 뒤 DONE 또는 ABORTED로 맞춘다.
  • IN_PROGRESS로 오래 남은 결제는 배치가 조회 API로 상태를 다시 맞춘다.
  • 토스 인증 후 일정 시간 안에 승인하지 않으면 결제가 만료된다. 문서상 시간이 10분과 30분으로 다르게 적혀 있어 실제 연동할 때 확인한다. READY로 30분 이상 남은 주문은 배치로 EXPIRED 처리한다.
  • 웹훅(결제 상태 변경 이벤트)을 받으면 본문을 그대로 믿지 않고, paymentKey로 조회 API를 다시 호출해 상태를 확인한다.
  • 환불은 POST /v1/payments/{paymentKey}/cancel (cancelReason)로 요청하고, 헤더에 멱등키(UUID)를 넣어 중복 취소를 막는다.
  • 아이템은 구매 즉시 적용되므로 환불 정책(예: 효과 적용 후 환불 불가)은 별도로 정한다.
  • 시크릿 키는 서버 환경변수로만 관리하고 프론트에는 클라이언트 키만 둔다.
  • IDX: (USER_ID, CREATED_AT DESC) (결제 내역 조회), (STATUS, CREATED_AT) (미완료 결제 정리)

  • 화면에는 작성자 닉네임과 학교명을 표시한다.
  • LIKE_COUNT는 GUEST_BOOK_LIKE를 INSERT·DELETE할 때 같은 트랜잭션에서 +1·1로 갱신한다.

속성설명타입제약조건

  • 작성자 정보는 조회 성능을 위해 비정규화해서 함께 저장한다.
