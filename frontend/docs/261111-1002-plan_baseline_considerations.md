## 3. 서버 연동 전에 우선 합의할 사항

### C1. DB 기준과 배포 구성을 하나로 통일 — 고위험(추론)

**확인:** P §5-1은 PostgreSQL을 선택했다고 적지만 같은 표의 설명에는 `AWS RDS → MySQL`이 남아 있다. E의 공통 규칙·테이블 목록은 MySQL 기준이며 `utf8mb4`, `AUTO_INCREMENT`, `DATETIME(6)`, `ON UPDATE` 등을 사용한다. P §5-2 아키텍처 이미지는 MySQL·React 중심의 구성이며, 새 표에서 설명한 ALB·별도 Redis 구성을 보여 주지 않는다. 본문도 해당 다이어그램이 바뀔 예정이라고 명시한다.

**권고:** 팀이 선택한 DB를 먼저 확정하고 그 엔진에서 실제로 실행되는 마이그레이션을 단일 기준으로 둔다. PostgreSQL 방향을 유지한다면 생성 ID·시각·수정시각 갱신·문자 비교/정렬·유일성·JPA 매핑과 테스트 DB를 함께 정리한다. 아키텍처 그림에는 정적 프런트·API·WebSocket 경로, ALB/WAS/Redis/DB, TLS 종료 위치·헬스 체크·오토스케일링 담당 구성요소를 구분한다.

**완료 센서:** 빈 실제 대상 엔진에 전체 마이그레이션·시드 실행, 유니크/외래키/점수 경계 테스트, 두 WAS에서 같은 Redis 상태를 조회하는 통합 검사. 문서 SQL이 실행된다는 확인 없이 ERD 확정 처리하지 않는다.

### C2. Redis 원본 점수와 DB 이력 사이의 실패·복구 계약 — 고위험(추론)

**확인:** E `USER`는 Redis를 개인 기여도의 원본으로 두고, `DB 외부에서 지키는 규칙`은 Lua 차감 후 USER_ITEM INSERT를 제시한다. P §6-2는 학교·학과·개인 점수를 1분마다 DB에 반영한다. 현재 목업은 로컬 reducer가 점수를 바꾼다(`src/utils/gameModel.ts:60~102`).

**추론:** Redis 잔액 확인·차감이 원자적이어도 DB 이력 저장까지 하나의 원자적 작업이 되지는 않는다. 차감 직후 장애가 나면 돈만 사라지거나 구매가 재처리될 수 있다. 배치가 오래된 개인 잔액을 덮어쓰면 소비 결과가 뒤집힐 수도 있다. “1분 배치”만으로 실제 허용 유실량·복구 기준은 정해지지 않는다.

**권고:** 아래 불변식과 장애 지점을 먼저 명세한다.

- 클릭은 학교·학과·개인에 한 번만 반영된다. 개인 구매/강화는 개인 잔액만 차감한다.
- 기여도 상품 구매와 강화는 동시에 요청돼도 잔액이 음수가 되지 않고, 구매/강화 결과와 근거 이력이 일치한다.
- 배치는 스냅샷/증분 중 무엇을 저장하는지, 경계 중 새 클릭·소비가 생겼을 때 어떻게 보존하는지, 중복/역순 실행·다중 WAS 실행을 어떻게 막는지 정한다.
- 구매 요청 ID, 처리 상태·재처리/보상, 배치 체크포인트와 버전, Redis 장애 시 쓰기 중단·복구 원천·허용 유실량을 정한다. 로그가 복구 원천이라면 단순 사후 저장이 아니라 누락·중복·재처리 계약이 필요하다.
- 클리커 ID 변경과 Redis의 클릭 세기 갱신도 하나의 논리적 작업으로 다룬다. 점수 담당과 상점 담당의 쓰기를 별개 구현으로 방치하지 않는다.

**가장 강한 대안:** 구매·강화의 잔액/이력을 DB 트랜잭션 중심으로 처리하고 Redis를 파생 상태로 쓰면 정합성 경계는 단순해지지만 고빈도 클릭 반영 전략을 다시 설계해야 한다. **권고:** 기존 Redis 우선 방향을 즉시 폐기하지 말고, 실패 주입 통합 테스트로 복구 경로를 증명한 뒤 채택한다. 이를 통과하지 못하면 내구성 중심 대안으로 바꾼다.

### C3. 1초 클릭 제출·멱등성·점수 확정 UX — 고위험(추론)

**확인:** P §6-2는 1초 묶음 제출이다. E의 중복 방지는 `SET submit:{userId}:{submissionId} NX EX 10`으로 제시돼 있다. 반면 현재 목업은 클릭마다 즉시 점수를 반영하며, M5 §6·§9는 이를 승인된 목업 단순화로 구분한다(`src/hooks/useMockGame.tsx:80~105`). 클릭 시퀀스 이미지에는 정상 경로만 있고 거절·재시도·부분 실패는 없다.

**추론:** 10초가 지난 동일 제출은 다시 인정될 수 있다. 또 중복 키 등록과 점수 갱신이 따로 실패하면, 점수가 빠졌는데 재시도가 차단되거나 반대로 중복 반영될 수 있다. 프런트가 클릭 수만 보내면 서버가 개별 클릭 간격을 확인할 수 있는지도 불명확하다.

**권고:** 제출 ID·사용자·세션·구간·클릭 수의 의미, 동일 ID/다른 본문 거절, 재전송 가능 기간, 멱등 기록 보관 기간, 기존 처리 결과 재응답을 정의한다. 중복 확인과 점수/제출 결과 기록의 논리적 원자성을 보장한다. 학교·학과·클리커·효과·치명타 결과는 서버가 검증/결정하고 클라이언트 값을 신뢰하지 않는다.

버프 만료·구매·강화가 1초 구간 중간에 일어날 때 어느 세기를 적용할지도 필요하다. 다중 탭/기기 합산 한도, 네트워크 단절·화면 백그라운드·복귀 시 재전송, 미확정 점수와 확정 점수의 표시/거절 보정을 정한다. 로컬 연출을 즉시 보여 주는 것과 점수 확정을 분리하면 현재 클릭감을 보존할 수 있다(권고).

**완료 센서:** 같은 제출 동시 재전송, 10초 이후 재전송, 응답 유실 후 재시도, 중복 키 기록 직후 장애, 구매/버프 만료와 경합하는 제출, 두 기기 합산 테스트.

### C4. 상품 모델이 커피와 이미지 변경을 실제로 표현하는가 — 고위험(추론)

**확인:** E `ITEM`에는 결제 수단·가격·지속시간이 있지만 효과 종류·배율·이미지 변경 대상 필드가 없다. `DURATION > 0`, USER_ITEM의 `EXPIRED_AT NOT NULL`, Redis TTL 적용은 모든 상품을 기간제 효과처럼 표현한다. N §2-1·N2는 커피와 학교/학과/개인 이미지 변경을 구분하고 현금 상품이 점수·버프에 영향을 주지 않도록 요구한다.

**권고:** 가격/결제 수단과 효과를 분리한다. 커피의 배율·기간, 이미지 상품의 대상 종류·대상 ID·검증된 이미지 참조·서버 변경 순서/버전이 계약에 포함돼야 한다. 상품 ID만으로 외부 하드코딩한다면 그 규칙의 단일 관리 위치와 주문 시점 스냅샷을 명시한다. USER_ITEM은 **보관함이 아니라 구매 이력**이라는 새 정의를 유지한다.

이미지 변경이 영구인지 기간제인지는 별도 결정 사항이다. 기존의 “즉시 적용” 지시는 지속기간까지 확정하지 않았다. 기간제라면 만료 후 기본 로고/이전 이미지/다음 유효 구매 중 어디로 돌아가는지, 겹친 유료 변경과 환불 순서를 정의해야 한다. 기본 로고와 사용자 변경 이미지를 한 URL에 덮어써 원본을 잃지 않게 한다.

### C5. 버프 교체와 Redis 재시작 복구의 충돌 — 고위험(추론)

**확인:** A §3은 버프 1개·비중첩·재구매 시 교체/만료 갱신이다. E `USER_ITEM`은 수정/삭제하지 않는 이력이며 `EXPIRED_AT > NOW()`인 행으로 효과를 복구한다고 적는다.

**추론:** 첫 커피가 아직 만료되지 않은 동안 두 번째 커피를 구매하면 미만료 이력은 2개다. 조회 조건만으로는 하나의 현재 효과를 결정할 수 없다. 향후 지속시간이 다른 효과를 추가하면 이미 교체된 효과가 복구 과정에서 되살아날 수도 있다. 이미지 상품까지 같은 복구 규칙을 적용하면 커피 버프와 뒤섞인다.

**권고:** 구매 이력과 현재 효과 포인터/효과 리비전을 구분하고, 복구는 서버가 확정한 마지막 유효 적용 상태를 재구성하도록 한다. 이력 불변을 지키면서 교체·취소·만료를 표현할 별도 적용 상태/이벤트를 둔다. 최소한 효과 종류별 적용 순서와 교체 사실은 복구 가능해야 한다.

**완료 센서:** 커피 2회 구매 뒤 재시작, 서로 다른 기간 효과 교체 뒤 재시작, 이미지 결제와 커피 동시 적용, 환불/만료 뒤 재시작에서 이전 버프가 부활하지 않음.

### C6. 현금 결제 이후의 이미지 적용·전파·환불 — 고위험(추론)

**이미 문서에 있음:** E `PAYMENT`는 서버 금액 결정, 본인 주문 확인, 조건부 상태 전이, PAYMENT_ID 유니크, 외부 승인 API의 DB 트랜잭션 분리, 타임아웃 시 실제 결제 조회, IN_PROGRESS 정리, 웹훅 재조회, 중복 취소 방지를 제시한다. 이 대책을 누락으로 보고하지 않는다. 결제 API 필드/허용시간의 현행 정확성은 이번에 외부 공식 자료와 대조하지 않았다.

**남은 공백:** DB에서 DONE·구매 이력이 커밋된 뒤 Redis 적용/이미지 변경 전에 장애가 발생하는 경로, 결제 주문에 묶인 이미지 대상·파일·적용 버전, 후속 이미지 변경 후 이전 주문 환불의 처리, 모든 열람자에게 변경을 전파할 이벤트·재연결 규칙이 충분히 정의되지 않았다. P §6-2의 WebSocket은 채팅 흐름이지 이미지 전파 계약이 아니다.

**권고:** 결제 상태와 효과 적용 상태를 구분하고, 내구성 있는 적용 대기 기록과 재처리 경로를 둔다. 이미지를 바꿀 학교/학과/본인 권한은 서버에서 확인하며, 오래된 주문이 나중에 승인돼 최신 이미지를 덮어쓰지 않도록 “마지막 변경”의 기준을 정한다. 적용 성공 이벤트에는 대상 ID·URL·버전을 포함하고 역순 이벤트 무시·캐시 갱신·재접속 최신 조회를 검증한다. 불쾌/불법 이미지 신고·차단과 유료 변경 취소 정책도 실제 결제 도입 전 필요하다.

**완료 센서:** 결제 성공 직후 프로세스 종료, 적용 이벤트 중복/역순, 권한이 바뀐 사용자의 지연 승인, 이미지 로드 실패, 나중 변경이 존재하는 이전 결제 환불, 서로 다른 사용자 2세션 즉시 반영.

2. **프런트 이전 경계:** 기존 Vite 목업 보존과 별도 Next.js 서비스 이식 중 경로를 정한다. Next.js 도입만으로 이 저장소를 즉시 전환할 필요는 없다. S3/CloudFront 정적 배포 방향을 유지한다면 선택한 Next.js 버전의 정적 빌드·라우팅·새로고침·결제 복귀 URL과 서버 의존 기능 사용 범위를 실제 빌드/배포로 확인한다.
3. **모델/API 표현:** 현재 문자열 학교 ID와 서버 BIGINT ID의 매핑, ID/대형 점수의 JSON 표현, 서버 시각·버프 만료시각·통화/단위·페이지 커서를 통일한다. 큰 정수를 프런트 number로 무조건 변환하는 계약은 피한다. 목업 ID가 실제 DB ID라고 가정하지 않는다.
4. **어댑터 분리:** 화면이 목업 reducer/상점 설정을 직접 서버 정책으로 사용하지 않도록 목업과 실제 API의 경계를 둔다. 클릭감·시트·레이아웃은 재사용하되 실제 잔액·권한·효과 결정은 서버 응답에 맞춘다. 구현 방식은 권고이며 새 구조를 이번 조사에서 구현하지 않았다.
5. **검증 단계 분리:** 모델/DOM 테스트 → 실제 서버 통합 → 두 사용자/두 WAS 동시성·장애 주입 → 실제 기기 → 목표 부하를 각각 관리한다. 목업 테스트 수로 이메일 발송·서버 어뷰징 방지·정합성·성능 완료를 증명하지 않는다.
